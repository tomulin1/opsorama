# Building dashboards with Opsorama

Opsorama draws a 3D scene of an operational space (a warehouse, shop, office, datacenter, restaurant…) inside an existing application. The **application owns** records, business rules, authentication, data sources and commands. Opsorama owns only the visual scene. Dashboards are the flagship use and what this skill covers; management games, interactive explainers and spatial visualizations are planned after the first release.

## Mental model

1. **Store** (`@opsorama/core`): `createSceneStore(definition?, settings?)` holds immutable scene nodes, settings and the selection. API: `getSnapshot`, `subscribe`, `upsert(node)`, `remove(id)`, `replace(nodes)`, `select(id | null)`, `configure(settings)`, `dispose`.
2. **Nodes**: visual records with a stable `id`. Kinds: `ground`, `zone`, `path`, `asset`, `marker`, and the primitives `shape`, `line`, `text`, `image` and `group` (see below). An asset node names a catalog model in `asset` and links to an application record through `entityId`. Positions are metres, Y-up, rotations in radians. Any asset or group can contain other nodes: a child sets `parentId` and uses the container's local coordinates, and it shows only while an asset container's `view` is `'peek'` or `'open'` (default `'closed'`; a group is always open). Change it with `setNodeView(store, id, view)`, opt into hover peeking with `peekOnHover: true`, and load children on first opening with `bindChildren(store, id, loader)`. The `building` model is the usual container; its own options (`type`, `size`, `cutaway`, `colors`) go in `building`.
3. **Assets** (`@opsorama/objects`): model factories grouped in kits. The renderer has **no built-in models**; pass a registry.
4. **Renderer** (`@opsorama/three`): `createSceneRenderer(container, store, { assets })`, or the React/Vue `SceneCanvas`, which creates and disposes the renderer for you.

## Steps

1. **Pick the objects.** Find models by name, purpose or category in `@opsorama/objects/catalog.json` (in an installed project: `node_modules/@opsorama/objects/dist/catalog.json`; in the Opsorama repository after `pnpm build:packages`: `packages/objects/dist/catalog.json`). Each asset entry has its `kit` and a `descriptor` with palette roles, options, counts, anchors, motion and interaction. Search it; do not read the whole file.
2. **Build the registry from those kits only**:
   ```ts
   import { createAssetRegistry } from '@opsorama/three';
   import { vehiclesKit } from '@opsorama/objects/vehicles';
   import { workItemsKit } from '@opsorama/objects/work-items';
   export const assets = createAssetRegistry(vehiclesKit, workItemsKit);
   ```
   Kit subpaths: `datacenter`, `displays`, `buildings`, `indicators`, `work-items`, `people`, `furniture`, `equipment`, `office`, `retail`, `fulfillment`, `vehicles`, `environment`, `surfaces`, `energy`, `events`, `restaurant`, `aquatics`, `animals`, `farm`, `laboratory`; the export is the camel-case name plus `Kit` (`work-items` → `workItemsKit`). `@opsorama/objects/handling` is not a kit: it holds the rules for which movable unit fits which place (`createHandlingState`, `handlingItemPolicy` for the core behavior runner's `itemPolicy`, optional `createMoveMode` and `bindMoveMode`). `catalogAssets` from `@opsorama/objects` has every model; use it only for prototypes. Add custom factories as another registry; a duplicate asset name throws.
3. **Map records to nodes** in application code: one node per thing the user should see, `entityId` pointing back to the record, labels and counts derived from the record. Model-specific settings go in the node's `options`, for example `options: { measurement: { value: 72, unit: '%' } }` on a gauge, `options: { building: { type: 'warehouse' } }` or `options: { surfaceLabel: { kind: 'text', text: 'DOCK 3' } }`; the descriptor lists them as `options.<name>` customization fields, and a catalog asset throws for an option it does not accept. Create the store with `createSceneStore(definition, settings, { validateAsset: assetValidator(assets) })` (`assetValidator` from `@opsorama/three`) so `upsert` and `replace` reject invalid nodes instead of the renderer failing later. Keep totals and identities in the application; a countable model shows a bounded `count`, and a disclosed `multiplier` expresses larger totals. Never encode quantity with `scale`.
4. **Mount the scene**:
   - React: `<DashboardProvider store={store}><SceneCanvas assets={assets} style={{ height: 480 }} /></DashboardProvider>`, with declarative `Ground`, `Zone`, `Path`, `Asset`, `Marker` or `EntityLayer` children if preferred.
   - Vue: the same components from `@opsorama/vue` (`:assets="assets"`).
   - Next.js: put the scene in a `'use client'` component; the page can stay a server component.
   - Plain JavaScript: `createSceneRenderer(element, store, { assets })`.
   Complete runnable projects: `examples/vanilla`, `examples/vite-react`, `examples/vite-vue`, `examples/next` in the Opsorama repository.
5. **Update from data**: on each application change, `store.upsert(node)` or `store.replace(nodes)`. React to clicks with `onSelect` (React `SceneCanvas` prop or renderer option; Vue `@select` event) and read `selection.entityId`; run business commands in the application, then update the store.
6. **Add panels if needed**: `@opsorama/react/ui` or `@opsorama/vue/ui` (`MetricCard`, `DataPanel`, `EntityInspector`, `ResourceList`, `ValueMeter`, …) or the DOM builders in `@opsorama/ui`, with `@opsorama/ui/styles.css`. Panels only present data the application passes in. To show the selected object itself in a detail panel, add `NodePreview` (React or Vue, `nodeId` plus the same `assets`) or `createNodePreview(element, store, { assets, nodeId })` in plain JavaScript: a live, slowly turning 3D copy of the node and what it carries. Use one per panel; each owns a WebGL context.

## Lifecycle rules

- `SceneCanvas` disposes its renderer on unmount. The store belongs to your component: call `store.dispose()` when the dashboard goes away for good. In plain JavaScript dispose in reverse order: listeners, subscriptions, `renderer.dispose()`, `store.dispose()`.
- Pass a stable `assets` registry (module constant or memoized). Replacing it remounts the renderer.
- A theme or palette change (`store.configure({ theme: 'midnight' })`) rebuilds every asset, shape, line, text and image node.
- The initial scene loads in slices behind a loading indicator. `onReady` fires before the first frame: `getAnchor` returns null for nodes not built yet, so await `renderer.loaded` before reading anchors. A node whose factory throws is reported once to `onError` (the message names the node) and stays empty while the rest renders; `validateScene` cannot check model anchors, so an `attachment.anchor` the model lacks is reported there too and the node sits at the owner's origin. A lost graphics context stops the renderer for good (`loaded` rejects if it happens before the first frame): remount it. `frame(id)` called early is applied when the build finishes.
- Settings: `theme` (`light` | `midnight`), `labels`, `grid`, `shadows`, `motion`, `paused`, `speed`, `zoom` (0.65–5), `selectionStyle` (`corners` | `glow`), `palette` (semantic material overrides), `camera` (see below). Reduced-motion and motion-off always win over per-object animation.
- Camera: `store.configure({ camera: { projection: 'perspective', fov: 40 } })` (`projection`, `controls` `pan` | `orbit` | `none`, `fov` 20–75°, `yaw`/`pitch` in radians, `overview` `ground` | `bounds`, `frameOnSelect`); replacing `camera` resets omitted fields, so spread the current value to change one. The default is the classic orthographic overview; `zoom` is the zoom for both projections. Move the camera with `renderer.frame(id, { fit: true, transition: { seconds: 1 } })`, `renderer.overview({ transition: {} })` and `renderer.setCameraView({ yaw, pitch, target, zoom }, transition)`; each resolves `'completed'` or `'interrupted'`, and moves are cuts with reduced motion or before the first frame (await `renderer.loaded`). In React/Vue, `useSceneRenderer()` and `useCameraView()` reach the camera from any component under the provider; one provider drives one `SceneCanvas`. `controls: 'orbit'` adds right-drag and Ctrl+drag orbit (mouse only; no keyboard focus, so add host buttons that call `setCameraView`). `renderer.followNode(id, { heading: 'behind', distance })` keeps the camera on a moving node until a pan, another move or removal (the promise resolves `'stopped'`, `'interrupted'` or `'removed'`); `renderer.playCameraPath({ keyframes: [{ frame: { nodeId, fit: true }, view: { yaw }, seconds: 2, hold: 1 }], loop })` returns `{ stop(), finished }`, and `validateCameraPath` names the bad field and the fix. Camera paths are host data, not scene data. Touch is off by default (the page scrolls over the scene, taps select); the mount-time `touchGestures` option (`touchGestures` prop on `SceneCanvas`) adds one-finger pan, two-finger pinch zoom and, with `controls: 'orbit'`, two-finger twist and vertical-drag orbit, and sets `touch-action: none` on the canvas, so enable it for full-viewport scenes, not ones embedded in a scrolling page.
- Shapes or catalog objects: use a catalog `asset` for anything real the user should recognize (a forklift, a rack, a person): it has a model, palette roles, anchors, counts and animation. Use `shape` (`{ type: 'box', size: [w, h, d] }`, `{ type: 'sphere', radius }`, `{ type: 'cylinder', radiusTop, radiusBottom, height }`; it stands on its position), `line` (`points` in local coordinates; `width` 0 is a 1-pixel line the pointer passes through, a wider line is a pickable tube; `dashed`) and `group` (no geometry; children name it in `parentId` and move, turn and scale with it) for data-driven or abstract content: chart bars, connections, simple markers and placeholders. They need no asset registry entry (`assets: {}` is fine for a scene of primitives only). Equal shapes of any size and color are instanced automatically; `opacity` below 1 opts a shape out. A shape without `color` takes the palette (its `state` role, otherwise `accent`). A click on a node that is not selectable selects its nearest selectable group (give the group an `entityId`), so make a chart's series groups selectable rather than every bar. `route`, `controller` and `transfer` work on shapes and groups too: a group with a route carries its contents. Only assets and groups can be parents; groups do not make their contents indoor. React and Vue export `Group`, `Shape` and `Line`; children still use `parentId`, the components do not nest. Example: `/examples/primitives`.
- Text and images: `{ kind: 'text', text: '42', size: 0.26, billboard: true }` draws up to 500 characters (`\n` breaks lines, no wrapping) with `size` as the capital-letter height in metres (0.05–20, default 0.4); the bottom of the text sits on its position and `align` (`left` | `center` | `right`) sets the anchor. Without `billboard` text lies in the node's x-y plane facing +z (`rotation: [-Math.PI / 2, 0, 0]` lays it on the floor); with `billboard: true` it faces the camera and ignores rotation, which suits value labels over bars. Without `color` it uses the palette `text` role. `{ kind: 'image', src: '/images/logo.png', size: [w, h] }` stretches the picture to `size` metres (keep the aspect ratio), shows a placeholder until it loads, and shares one texture per `src`. `src` must be relative, `http(s):`, `blob:` or `data:image/`; other schemes fail validation (`image-src`). Images from another origin need `Access-Control-Allow-Origin` on their server; a failed load keeps the placeholder and reaches `onError` with `name === IMAGE_LOAD_ERROR` (from `@opsorama/three`) naming the node and URL. Text and images take no route or controller (put them in a group), are never instanced and cast no shadow; clicks hit them like shapes. Canvas text is not accessible text: keep essential values in labels or host HTML as well. React and Vue: `SceneText` and `SceneImage` (named so they do not shadow the DOM `Text` and `Image`).
- Engine hooks: `onPointer` (renderer option; React `onPointer` prop, Vue `@pointer`) reports `down`/`up`/`click`/`enter`/`leave`/`move` with `nodeId` (nearest node, selectable or not, grounds included; null over empty space), `ancestors`, world `point` (ground plane y = 0 on a miss), modifiers and `source`; call `event.preventSelection()` in a `click` to keep the selection (for example a click on the floor that sends a robot). `renderer.onFrame(listener, { step: 1 / 60 })` (React/Vue `useSceneFrame`) runs a fixed simulation step that stops while paused and keeps running with motion off; without `step` it runs once per frame. `plugins: [{ name, setup(context) { ...; return cleanup } }]` (mount-time; keep the array stable in React and Vue) adds Three.js objects through `context.scene`; remove and dispose them in the cleanup, and read nodes with `context.nodeObject(id)` without changing them.

## Common mistakes

- Calling `createSceneRenderer(container, store)` without `assets` (a type error; at runtime "Unknown asset").
- Importing `catalogAssets` in production scenes that use a few kits (much larger bundle).
- Putting business state (prices, owners, permissions) on nodes instead of in the application.
- Setting model options such as `measurement`, `surfaceLabel` or `building` directly on the node instead of inside `options`.
- Using `scale` to show quantity, or inventing unit identities for a count.
- Mounting a renderer per list item; use one scene with many nodes.
- Rendering the scene on the server in Next.js; keep it in a client component.
- Putting information users must read only into a `text` node; canvas text is invisible to screen readers.
- Loading an `image` from another origin whose server sends no `Access-Control-Allow-Origin` header; serve it from your own origin or enable CORS.

## Verify

- **Validate the scene first, without a browser.** Run `validateScene(definition, { validateAsset: assetValidator(assets) })` from `@opsorama/core` (with the same registry as the renderer) on every scene you write or change, for example in a unit test or a short script, and repeat until it returns `[]`. Each problem names the value by JSON Pointer `path` (`/nodes/3/route/speed` is `definition.nodes[3].route.speed`), a stable `rule` (descriptions in `SCENE_RULES`), a `message` and a `fix` that states the expected format or allowed values; `nodeId` names the node. Apply the `fix`. `severity: 'warning'` is only `unknown-key`: a key the renderer ignores, usually a typo (the fix suggests the nearest known key) or a model setting that belongs in `options`. The store's `SceneValidationError` carries the same list in `error.problems`. Editors and other tools can use the JSON Schema `@opsorama/core/scene-definition.schema.json`; it does not check IDs, parents or model options, so `validateScene` is the final check.
- Type-check, then open the page: the scene renders, selection reports the expected `entityId`, updates move nodes without remounting.
- Check that unmounting removes the canvas and that no subscriptions remain.
